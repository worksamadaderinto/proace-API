# Vault production secrets

Local development keeps ignored `.env` files. Production deployment uses GitHub OIDC, verified TLS and a narrowly scoped Vault KV v2 read policy. The deploy job alone has `id-token: write`. Configure the repository's protected environment with nonsecret `VAULT_ADDR` and `VAULT_ROLE` variables, environment approvals and branch protection. Do not add a long-lived Vault token to GitHub. `scripts/vault_ci.py` requests the `proace-deploy` audience, writes one credential document as a temporary mode-0600 file, revokes its Vault token, and never exports the document through `GITHUB_ENV`. Cleanup runs after success or failure. Private-CA deployments must install the CA on the runner and set the nonsecret `VAULT_CACERT` path; never disable TLS verification.

Use a GitHub JWT auth role with exact repository name AND numeric repository ID, protected environment subject, ref and workflow_ref claims. Bind `bound_audiences` to `proace-deploy`, token TTL 5 minutes/max 10 minutes and only this component's exact deployment policy. Policies also allow token self-inspection/revocation; runtime policies allow self-renewal so no default policy or broader token access is needed. Configure GitHub's OIDC discovery URL and issuer as `https://token.actions.githubusercontent.com`. A renamed repository requires intentional role review. The provided role example binds main; master needs its own explicit role or an intentional list of exact allowed refs/workflows. Do not grant wildcard repository access. Pull requests never receive production credentials.

Vault files and temporary credential documents must not be uploaded as artifacts, cached or committed. Vault prevents persistent secret copies in workflows and production .env files; compromised hosts, deployment tools and authorized processes can still read the secrets they use. Revoke/rotate credentials after compromise. The integration is prepared locally; no live Vault or provider deployment has been verified.

## New HostGator Vault instance

The self-contained templates are in `deploy/vault/`. Replace every example hostname/repository ID before use. Install the matching Vault CLI on the host from HashiCorp's verified release, provision a TLS certificate/key owned by the Vault service, and restrict network ingress. `compose.yaml` binds the TLS listener to loopback: terminate/reverse-proxy your public Vault hostname to **HTTPS** `127.0.0.1:8200` with upstream certificate verification and matching TLS server name, or deliberately expose 8200 only behind a firewall with end-to-end TLS. Never proxy plaintext to this TLS listener. Configure `api_addr`, `cluster_addr` and Agent addresses to your real names. The Raft volume must be writable by the image's Vault user; the private key must be readable by that user only. Verify image provenance and upgrades under your release policy.

Start only this stack with `docker compose --env-file /dev/null -f deploy/vault/compose.yaml up -d`. This is a production Raft/TLS configuration, not Vault dev mode. Initialize/unseal interactively using `vault operator init` and `vault operator unseal`; transfer unseal shares and the initial root token directly to separate trusted custodians. Never paste their output into CI, app logs, this repository or chat. Configure audit logging with restrictive ownership and protected retention, encrypted off-host Raft snapshots, a tested restore/unseal procedure and monitoring of sealed/unavailable states. The single-host configuration is not HA and shares the VPS trust/failure boundary. Auto-unseal requires a separately configured KMS/HSM; no fake auto-unseal is configured here.

Enable KV v2 at `kv`, AppRole at `approle` and JWT auth at `github`. Install the exact policies from `policies/`. Create the API AppRole from `roles/api-approle.json`; it may read only the API runtime path. Install GitHub deployment roles from the example with each component's repository ID, environment, policy and corresponding path. Revoke the bootstrap root token once non-root operational administration and recovery access are verified. Routine apps/CI must never receive a root token or permissions to write policies/secrets.

## Runtime secrets and safe migration

`kv/proace/production/api` (CLI logical path; HTTP/policy path is `kv/data/proace/production/api`) contains a JSON object with the existing Django setting names. Import exact existing production values securely from a restricted file using `vault kv put -mount=kv proace/production/api @/secure/operator-input.json`; avoid CLI `KEY=secret` arguments and shell history. The input must include `SECRET_KEY`, `PASSWORD_PEPPER_KEYS` (object or JSON string), `POSTGRES_PASSWORD`, a strong `REDIS_PASSWORD`, `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD`, dedicated `MINIO_ACCESS_KEY=commerce-media` and `MINIO_SECRET_KEY`. Add actual configured Stripe/webhook, Resend/from-address, Firebase admin JSON, carrier, ClickBank, observability and infrastructure-sync credentials under their existing names. Never put service credentials in the public file or client bundles. Do not store example dummy keys in production. Firebase admin JSON can be a nested object; the reader serializes it for existing settings.

Preserve the existing Django SECRET_KEY, full pepper keyring, database password and media credentials exactly during migration. Do not regenerate peppers or reseed users. Provision the dedicated media user/bucket permissions with a trusted MinIO administrator before the first API deployment; deployment does not recreate MinIO users or silently grant root access. Existing PostgreSQL volume passwords are not changed by `_FILE`; explicit coordinated ALTER ROLE is required for later rotation. Copy `config.example.json` to `/etc/proace/config.json` and fill real nonsecret domain/database/config values. Select the existing pepper ID. OAuth client IDs/public Firebase configuration may be public, but API keys and credential JSON belong in Vault. Set allowed hosts to include notification-stream when using that consumer, secure proxy/CSRF origins to the actual web domain and preserve the approved Nginx allowlist in `/etc/proace/allowed-ips.conf`.

Create host group `proace-api-secrets` with GID 2000 and a non-login `proace-vault` account (UID 2000). Install the Agent HCL/templates under `/etc/proace/vault`, the role ID as a restricted file, and the supplied systemd mount/service files under `/etc/systemd/system`. Install `tmpfiles.conf` as `/etc/tmpfiles.d/proace-vault.conf`. The host Agent needs a verified HTTPS route to Vault. `/run/proace-vault` must be a tmpfs mount; the API directory is mode 0750, owned by the Agent with group 2000. Agent renders files 0440. Containers add group 2000 and mount only the API directory read-only. Atomic directory-file replacement is visible because the directory is mounted. Keep bootstrap directory mode 0700 owned by the Agent.

Generate a response-wrapped, one-use SecretID with a trusted provisioning identity (`vault write -wrap-ttl=5m -f auth/approle/role/proace-api/secret-id`), deliver only its wrapping token via a secure channel to `/run/proace-bootstrap/wrapped-secret-id` with mode 0600 owned by the Agent, then start the service. Do not log the wrapping token. The Agent validates its creation path, unwraps it, removes the file and renews its periodic token in memory; there is no token sink. Every Agent restart/host reboot needs a fresh wrapped SecretID. Configure your secure bootstrap procedure accordingly; do not persist a reusable SecretID to bypass this. After mount startup, ensure the API directory exists through systemd-tmpfiles before Agent launch.

`PROACE_CONFIG_MODE=vault` reads settings from JSON directly, never exporting them to `os.environ`, and ignores application-setting env overrides. Missing/invalid/restricted-file configuration fails closed; debug must be disabled. Local mode retains existing dotenv behavior. The process snapshots files until restart; Agent refresh alone is **not** application rotation. After updating Vault, verify rendering, coordinate database/MinIO/provider-side credential changes, then recreate API, notification-worker, notification-stream and celery-beat together. Restart Redis after password changes and all consumers together. Keep old pepper keys until no stored hash references them. Treat outages explicitly: running processes retain their snapshot; new processes fail without readable rendered secrets. tmpfs requires repopulation after reboot.

The standalone production Compose preserves `commerce-server` volume identities and the existing external `commerce-network`; it does not inherit local env_file/source mounts. Verify existing project/volume names before first migration and take tested database/media/Vault backups. Deploy through the protected CI image handoff after host setup. The verified API/stream images must be activated before `sh deploy/hostgator/deploy.sh` can run. The script refuses non-tmpfs secrets, uses the checked local image IDs without rebuilding, starts infrastructure, migrates before starting new workers, then verifies readiness. See [supply-chain controls](supply-chain.md) for the archive, platform and rollback prerequisites. It uses the host public config and does not upload application secrets from CI. After successful cutover, securely retire legacy production .env copies, old GitHub application secrets and backups containing them according to retention policy; revoke superseded deployment tokens. Never delete local .env or data volumes as part of this migration. Rollback must use code that supports the existing password hashes and Vault configuration.

## Deployment credential documents

- `api-deploy`: `HOSTGATOR_HOST`, `HOSTGATOR_PORT` (optional, default 22), `HOSTGATOR_USER`, absolute `HOSTGATOR_DEPLOY_PATH`, `HOSTGATOR_SSH_PRIVATE_KEY`, `HOSTGATOR_SSH_KNOWN_HOSTS`. Verify host fingerprints independently; host-key checking is strict. Give the deployment account only required host access. No database/provider keys in this document.
- `web-deploy`: `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`. Vercel remains the web provider.
- `mobile-deploy`: `EXPO_TOKEN`, `APPLE_ID`, `ASC_APP_ID`, `APPLE_TEAM_ID`, `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON`, optional `APPLE_APP_SPECIFIC_PASSWORD`. EAS remains the native build/submission provider.
- `monitoring`: independent runtime document, separate AppRole and reader group; see monitoring's own docs. Monitoring stays stopped until its hosting is selected.

## Third-party boundaries

PostgreSQL's official `_FILE` entrypoint reads the password file into its internal process environment. MinIO's file credential support likewise copies root credentials into internal environment variables. Those services receive file **paths**, not secret values, in Docker configuration, but this is not an absolute no-process-environment guarantee. The API reads secrets directly. EAS requires its release token in a child process environment; Vercel CLI receives a masked token argument. These are transient release-tool exposures, not application bundle content. Keep release runners isolated, avoid command tracing/process dumps and rotate scoped service tokens. Vault cannot protect secrets from a compromised authorized process or root host.

References: [Vault Agent AppRole](https://developer.hashicorp.com/vault/docs/agent-and-proxy/autoauth/methods/approle), [Vault templates](https://developer.hashicorp.com/vault/docs/agent-and-proxy/agent/template), [GitHub workload identity](https://developer.hashicorp.com/well-architected-framework/secure-systems/secure-applications/ci-cd-secrets/github-actions).

Technical-admin password changes still use existing MinIO/Grafana synchronization. Coordinate their matching Vault values through a privileged operator rotation flow before restart; the application read-only role cannot write Vault. Do not expect direct provider password updates to update Vault automatically.

Production Redis runs directly as its image-defined `redis` user so its supplemental secret-reader group survives startup. Verify the existing Redis volume is writable by that image user before cutover; never delete the volume to fix ownership.

Install `docker-vault.conf` as `/etc/systemd/system/docker.service.d/proace-vault.conf` and reload systemd during the planned host setup. Docker must start after the runtime tmpfs mount, so restarted containers bind the real memory filesystem rather than an underlying disk directory before mount activation. The Agent then creates the API directory with the supplied tmpfiles rule. Until fresh wrapped bootstrap credentials are provided and templates render after reboot, new application processes fail closed and retry through their restart policy. Do not restart the entire Docker daemon during routine application releases. Verify boot ordering in a maintenance window before production cutover.

A tmpfs mount is memory-backed but can be swapped by Linux. Configure the production host with swap disabled, encrypted swap, or the kernel-supported tmpfs `noswap` option after checking HostGator kernel support; do not assume tmpfs alone prevents all disk persistence. Include host crash-dump access in the same secret protection boundary.
