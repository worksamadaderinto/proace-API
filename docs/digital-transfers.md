# Resumable digital content

## Purchased-file previews

Order responses include download links only for paid orders in an eligible fulfillment state. The download and preview endpoints verify that same eligibility on every request.

The authenticated purchased-file endpoint accepts `preview=1` for PDFs, raster images and supported audio/video extensions. It uses the purchased asset filename, not the product title, to choose an explicit MIME type and inline disposition. Ordinary downloads retain attachment disposition. HEAD and byte-range requests preserve the same order ownership, payment, revocation and variant checks. Preview responses remain private/no-store with nosniff and restricted framing. Non-PDF responses carry a sandbox policy; PDFs use the browser's isolated PDF renderer because HTML sandbox restrictions can block native PDF loading. HTML, SVG, EPUB, archives and other unsupported types return 415 for inline requests and remain attachment-only downloads. Browser codec and PDF-viewer support varies. External files retain the existing bounded retrieval policy rather than acquiring a large-file streaming guarantee.

Managed purchased assets and seller/staff inspection endpoints support single HTTP byte ranges. Every request, including HEAD and resumed ranges, passes the existing ownership/role/payment/refund checks. Responses expose Accept-Ranges, a stable ETag, Content-Length and, for partial content, Content-Range. Invalid or unsatisfiable ranges return 416. If-Range prevents combining different editions. Managed MinIO reads request only the selected range from S3; local storage seeks directly. External URLs remain the existing bounded retrieval path and do not gain a multi-gigabyte resume guarantee.

Seller product endpoints expose `digital-upload/`: GET returns upload limits; POST accepts start, sign, part, complete and abort. Sessions belong to the authenticated seller and product, expire after 24 hours, and have at most four active sessions per seller. The server default limit is 5 GiB (`RESUMABLE_DIGITAL_MAX_BYTES` in validated runtime configuration); ordinary cover/artwork/variant multipart limits remain unchanged. The part size is 8 MiB. Keep all staging and completed digital originals private.

The clients fingerprint all file chunks before starting, then reuse server-recorded completed parts when the original file is selected again. This manifest identifies the selected file; it is not a claim that the server independently recomputes a whole-file SHA-256 after a direct storage upload. MinIO part sizes and provider ETags are checked before completion. MinIO uses multipart assembly; the local filesystem fallback uses bounded buffers and a temporary assembly file, so local disk must accommodate the complete asset plus staging parts.

For MinIO, parts upload directly using 15-minute scoped presigned URLs. This avoids Vercel request body limits and does not expose permanent storage credentials. Configure MINIO_PUBLIC_URL as the actual public HTTPS storage endpoint and allow the actual web origin in MinIO CORS for PUT. Keep multipart originals outside public bucket policies. Do not log presigned URL query strings. The authenticated completion endpoint rechecks access before attaching the object to the product. Configure storage lifecycle cleanup for abandoned multipart objects as additional protection.

Large-content onboarding saves an unpublished product with its required cover first, uploads the content, then applies the requested publication/scheduling settings. A failed transfer leaves a draft; use that draft's media page and select the same original file to resume. A digital product cannot be published or scheduled without content. Large main content is supported; option files retain their existing upload limit and should be added after the main asset.

`store.cleanup_digital_uploads_task` runs hourly through the existing worker/beat stack. The same cleanup can be run with `python manage.py cleanup_digital_uploads`. Apply migrations before serving the new endpoint and recreate api, notification-worker, notification-stream and celery-beat after shared runtime updates. Never delete storage volumes to refresh code.

Web uses bounded range requests and direct-to-disk saving when the browser exposes the save picker. Unsupported browsers retain the standard browser download option with explicit guidance; that fallback still depends on browser/hosting limits. Do not promise a 4 GiB browser download through a Vercel function from API range tests alone. Native mobile explicitly persists partial cache files and validators per signed-in user and resumes via bounded ranges; revoked access is checked again. Actual multi-gigabyte transfers, app termination/resume, free-space failures, MinIO CORS and signed-device behavior need deployment/device acceptance. Sparse-file and mocked provider tests verify protocol behavior without allocating or transferring 4 GiB over the network.
