# API repository agent rules

## Shared engineering rules

- Do not hardcode business data, user/store identities, recipient addresses, prices, counts, statuses, permissions, provider identifiers or deployment settings. Read them from authoritative backend records, validated configuration or existing shared constants. Keep intentional policy constants centrally defined and documented; keep illustrative fixtures confined to tests/development. Never substitute fabricated data for missing production data; show an honest empty/unavailable state.
- Never implement implicit state machines. All domain lifecycles (orders, fulfillments, refunds, funding reservations, coupon redemptions, and store memberships) must be governed by explicit, validated transition graphs with strict transition guards and irreversible terminal state boundaries (e.g., cancelled orders cannot be reopened or mutated; expired/cancelled redemptions must release capacity atomically). Reject invalid transitions with domain errors rather than silently coercing or overwriting state.
- Decouple all external SDKs, remote services, and third-party integrations (payment processors, shipping carriers, merchant payouts, object storage, mailers, notification dispatchers, social auth providers, search indexers, push gateways, and ML/vision clients) from core business logic using Pythonic Dependency Injection (Ports & Adapters). Define typed interfaces with `@runtime_checkable` `typing.Protocol`, register pluggable adapter backends in `settings.py` via `*_BACKEND` configurations, and use default-parameter injection in services and views (`def action(..., gateway: Any = None)` with fallback to `get_<gateway>()`). Always provide deterministic `Mock*` adapters alongside production implementations to allow offline, fast, and repeatable testing without network dependencies or monkey-patching. Never hardcode external carrier tracking URLs or remote API endpoints in business models or views; configure them centrally in `settings.py`.
- Apply disciplined workload segregation between async and Celery: use asynchronous execution (asyncio / coroutines / non-blocking I/O) where best suited for high-concurrency, I/O-bound tasks (such as concurrent carrier rate fetching, non-blocking SSE/realtime streams, and parallel upstream API calls), and use Celery background task workers for CPU-bound workloads (such as image manipulation, preview watermarking, digital asset derivation, report generation, and heavy aggregations) as well as durable deferred background processing.
- Give each recipient only the data appropriate to their identity, role, ownership and purpose. Derive recipients and record scope on the server, enforce authorization and tenant isolation, and minimize fields in API responses, screens, emails, notifications, exports and logs. Never reuse another user's/store's records or send a global payload to every recipient. Test permitted delivery and cross-user/cross-store exclusion when changing recipient-scoped behavior.
- This is an independent Git repository. Its .github/workflows/ci-cd.yml runs from this repository root; no parent checkout or sibling source is required by CI. Keep its own history, lockfiles, credentials and deployment settings. Never invent a remote URL or push without authorization.
- Maintain README.md as the repository entry point. All other narrative documentation belongs in docs/; AGENTS.md, other instruction files and bug audits are exceptions. Bug audits belong exclusively in `qa-report/bug-audit/`, never `docs/`. Update relevant docs and README in the same change. If the optional parent workspace is present, keep its overview synchronized too.
- Use explicit types, clean formatting and readable functions: 2-space TypeScript/TSX and 4-space Python. Avoid any. Declare API validation and OpenAPI schemas explicitly. Serialize non-primitive values through serializers or explicit primitive conversion.
- Handle failures deliberately. Return actionable sanitized guidance; never expose credentials, tokens, personal data, SQL, internal paths or stack traces. Keep diagnostics in trusted logs. Never silently swallow business/provider failures.
- Keep local secrets in ignored .env files; production service secrets use Vault Agent files and deployment credentials use GitHub OIDC to Vault. Do not reintroduce production .env or long-lived Vault tokens in GitHub/hosting settings. EXPO_PUBLIC_ and NEXT_PUBLIC_ settings are public bundle data, never secrets. Preserve auth, tenant isolation and server-derived ownership. Django owns prices, stock, eligibility, tax and financial outcomes; clients are not authoritative.
- Browser web requests use the same-origin /api proxy with HttpOnly cookies. Native mobile uses its existing SecureStore adapter and bearer transport; never persist tokens in browser storage, AsyncStorage, URLs or logs.
- Support accessible light/dark themes. Main listings need debounced search, orthogonal filters, accurate pagination, reset controls and meaningful empty states, synchronized with API filtering.
- Preserve commerce policies: 14-day post-delivery refund/review escrow, 24-hour pre-shipment cancellation, atomic inventory/wallet recovery, 15% standard marketplace commission and 0% commission for Official and invited Partner stores. ClickBank listings use external checkout and never contaminate native carts. Keep policy/help content aligned with authoritative API behavior.
- Preserve destination tax precision and immutable order/address/tax/payment snapshots. Emails use actual recipient-scoped backend records, omit missing optional rows, preserve legitimate zero values and escape user content. Persist notification delivery outbox rows transactionally and dispatch after commit with idempotency/retries. Never claim live delivery from rendering/outbox tests alone.
- Development seeding uses populate_fake_data only and preserves existing technical-admin passwords. Never reseed during deployment, delete volumes to refresh code, or overwrite credentials as a test workaround.
- Run this repository's verification suite before concluding implementation/refactoring. Run affected peer/integration checks when changing shared contracts, but do not require sibling source for an isolated checkout. Report failures/skips honestly. Rebuild/recreate only affected local consumers, apply necessary migrations and verify status/health; a successful image build alone is insufficient.
- Never write fake, tautological, or vacuous tests. Tests must execute real application code paths, exercise genuine business logic, and validate actual state changes, edge cases, and failure modes against authoritative models and contracts. Do not write tests that merely assert tautologies, mock out the very behavior under test without exercising system logic, or exist solely to artificially inflate pass counts or coverage. Every test must be capable of failing if the implementation breaks or regresses.
- Write every bug audit, its findings and summaries explicitly to this repository's ignored `qa-report/bug-audit/` folder. Create the folder when needed. Never write bug-audit reports or artifacts to `docs/`, another documentation directory, `qa-reports/bug-audit/` or directly to `qa-report/`. Keep all QA output under the single ignored `qa-report/` root; performance and security reports use `qa-report/performance/` and `qa-report/security/`. Do not recreate a `qa-reports/` folder. Retain only the latest completed performance/security run per category, publishing its summary/artifacts before removing superseded output. Never delete unrelated reports, fixtures or source.

## Code DRYness and duplication policy

Code MUST be DRY. Do not duplicate definitions or logic. When the same constant, type, validation, or block of logic appears in more than one place, abstract it into a shared helper/utility and reuse it. Flag copy-pasted logic and repeated literals/definitions that should be centralized.

## Code simplicity, understandability, and readability policy

Codebases across the monorepo MUST be kept as simple, understandable, and readable as possible:
- **Simplicity first (KISS & YAGNI)**: Write the most direct, straightforward solution that completely and correctly solves the problem. Strictly reject premature generalizations, speculative future-proofing, unnecessary abstraction layers, and clever or esoteric programming tricks.
- **Self-documenting readability**: Code must be immediately comprehensible at first glance. Use clear, descriptive, domain-accurate names for variables, functions, components, and types. Avoid cryptic abbreviations, dense one-liners, and opaque structures.
- **Small, focused units**: Functions, methods, and components must adhere to the single-responsibility principle. Break down long, tangled, or multi-purpose routines into small, focused, easily testable helpers.
- **Flat, direct control flow**: Favor guard clauses, early returns, and linear execution over deeply nested conditionals, callback pyramids, and convoluted branching.
- **Minimal cognitive load**: Optimize for the human reader. Avoid convoluted metaprogramming and hidden side effects. When complex domain logic or edge cases cannot be simplified further, document the *why* with concise, meaningful inline comments.

## Strict prohibition of AI-themed and emoji-style icons in UI

Strictly forbid using AI-themed icons (e.g. `Sparkles`, `Bot`, `Wand`, `Brain`, `Stars`, `Zap` as AI indicators) and raw unicode emojis (e.g. `🎉`, `📅`, `💵`, `📦`, `🔒`, `⚠️`, `📢`, `🔥`, `⚡`, `🤝`) as UI icons across all clients (web, mobile, or any frontend/app).
- **Professional commerce design language**: Always use standard, domain-appropriate vector icons from the project's designated icon library (`lucide-react` on web, `@expo/vector-icons` on mobile, or clean SVGs).
- **Never use emojis as icons**: Do not embed raw unicode emojis in table headers, cells, cards, tooltips, chart ribbons, modal titles, badges, or buttons. If an icon is needed for a date, amount, package, or status, use standard vector icons (`<Calendar />`, `<DollarSign />`, `<Package />`, `<Clock />`, `<Check />`) with proper alignment and typography.
- **Zero AI-themed gimmickry**: Never decorate visual search, catalog results, product recommendations, analytics cards, or categories with sparkle/magic/bot icons. Represent features with accurate, concrete domain icons (e.g. `<Camera />` for photo search, `<Tag />` or `<Search />` for catalog results, `<Heart />` for beauty).

## Database query efficiency and zero-tolerance N+1 policy

Strictly forbid N+1 query patterns across all API endpoints, serializers, services, and background workers. Every list endpoint, search view, and batch serialization must execute in bounded, O(1) database queries relative to the number of records returned.
- Eliminate per-row database hits proactively: use `select_related()` for single-valued relationships (ForeignKey, OneToOneField) and `prefetch_related()` (with explicit `Prefetch` querysets where appropriate) for multi-valued relationships (ManyToMany, reverse ForeignKeys) and generic foreign keys (`GenericForeignKey`).
- Never execute raw `.filter()`, `.get()`, `.count()`, `.exists()`, or `.aggregate()` queries inside serializer methods (`SerializerMethodField`, `to_representation`), model properties, or loops over querysets.
- Compute counts, sums, existence, and rollups in SQL using annotations (`annotate()`, `Subquery()`, `Exists()`), or batch-compute and cache lookup maps on the serializer context (e.g. `self.context['batch_data']`) across the paginated page.
- Protect list endpoints against query regressions with automated query budget tests using `CaptureQueriesContext` / `assertNumQueries`.

## API verification and deployment

Run `.venv/bin/python -m pytest server/`. Shared backend code affects api, notification-worker, notification-stream and celery-beat; select affected consumers from actual dependencies. Rebuild with `docker compose -f server/compose.yaml up -d --build --no-deps api` and add affected consumers. Apply migrations through the updated API container and verify health. HostGator deployment uses this repository's protected production environment, Vault OIDC deployment credentials and Vault Agent runtime files. It deploys API and its edge only. Preserve the administrative triad, dedicated media credentials and existing Grafana/MinIO synchronization behavior.

## Persistent severity-based QA reporting

- Keep active bugs, functional/UI issues, reliability gaps and security vulnerabilities in the repository's ignored `qa-report/bug-audit/` directory, exclusively in reusable severity files: `Critical.md`, `High.md`, `Medium.md`, and `Low.md`. Create this fixed set once and reuse it for all later audits. Do not create per-audit, per-date, per-feature or per-issue Markdown reports, and never place audit findings in `docs/`.
- Classify severity by demonstrated impact, reach and exploitability: Critical for immediate severe compromise or widespread irreversible loss; High for major security, authorization, financial or core-workflow failures; Medium for material but limited-impact failures; Low for minor usability, visual or low-impact defects. Identify the issue category within the entry; all categories share these severity files.
- Give every new issue its own heading containing a clear title and its actual discovery date/time in Africa/Lagos, including the UTC offset: `## Product race condition — YYYY-MM-DD HH:mm WAT (UTC+01:00)`. Do not invent discovery timestamps for older findings. Preserve the original timestamp when updating an existing issue.
- Each entry records affected component/files or flow, reproducible evidence, actual impact, and the verification needed to close it. Sanitize evidence; never include credentials, tokens or unnecessary personal information. Update an existing entry for the same root cause instead of duplicating it on subsequent audits. Move the entry if its severity changes.
- After fixing an issue and passing the relevant verification, delete that issue's entire section from its severity file, preserving unrelated open findings. Do not keep resolved entries, strike-through histories or duplicate fixed-issue reports in the active ledger. Keep an issue open when verification is incomplete or blocked, and state what remains. If a severity file has no open issues, retain the reusable file with a brief “No open issues” statement. Remove that statement when adding a new issue.
- These files are the cumulative active QA ledger, not a claim that untested areas have no bugs. Apply this workflow to every future bug audit. Preserve unrelated existing reports/artifacts; do not bulk-delete or fabricate classifications/timestamps for historical reports during instruction updates.

## Bug-audit folder contents

- After every bug audit, `qa-report/bug-audit/` must contain only the four persistent severity files: `Critical.md`, `High.md`, `Medium.md`, and `Low.md`. Reuse these files, including an empty “No open issues” file when appropriate. Do not retain any other files or subfolders there: no dated summaries, separate issue reports, screenshots, logs, JSON, traces, HTML or evidence archives.
- Put the minimum sanitized reproduction/evidence and closure criteria inside the relevant issue section. Temporary audit scratch output may be used while working, but remove audit-generated scratch artifacts before concluding; do not relocate extra bug-audit reports/artifacts into docs or another QA directory to evade this rule. Preserve application source, tests, fixtures, user data and separate non-bug-audit performance/security outputs.
- Publish and verify the replacement severity entries before removing superseded audit reports. Remove fixed findings only after their relevant fix verification passes; retain unresolved or blocked findings with honest status. Consolidating historical reports must not invent discovery timestamps, convert acceptance gaps into confirmed exploits, or silently erase unresolved findings.

## Supply-chain review policy

Keep Actions pinned to verified full commit SHAs, container images to verified digests, and deployment CLIs in the separate exact-version tool lockfile. Install Node dependencies with lifecycle scripts disabled; any necessary exception must be version/integrity-scoped, reviewed, documented and tested without credentials. Never run package installers after obtaining deployment credentials. Review lockfiles, added transitive dependencies, registry/source changes, install hooks, workflow permissions and auth/payment changes. Do not auto-merge dependency updates or disable security gates to force a release. Never treat hashes or passing scanners as proof that code has no backdoor. Repository rules and CODEOWNERS require actual GitHub configuration and eligible independent reviewers; do not claim they are active from files alone.
